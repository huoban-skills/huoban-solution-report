# 报告写作规范

模板骨架见 assets/template.html，本文只管「往里填什么、怎么写」。

## 全局口径

- 读者是客户决策层。语言是诊断，不是推销：陈述现状事实与后果，不喊口号，不用感叹句。
- 读者底线画像：默认读者是**不懂系统的业务经营者**，全篇必须让这样的人读懂。素材盘点抽出的读者画像（给谁看、数字化熟悉度、最关心哪本账）只用来决定举什么例子、强调哪类收益（省人力/管理可控/提效/控风险），不用来放开术语。
- 业务语言：所有能力用业务动作和业务结果描述，不出现表结构、字段、自动化规则、数据流转等系统实现细节。对照示例：

  | 别这么写 | 这样写 |
  | --- | --- |
  | 设置到期日期字段触发自动化 | 合同到期前系统自动提醒续签 |
  | 配置了表单关联与自动化 | 采购单提交后，入库单自动生成，不需要手动重新填写 |
  | 设置了审批流 | 订单超过 5000 元自动走主管审批，不用再人工转发 |
  | 调整了看板计算公式 | 首页看板实时显示本月销售总额和各产品占比 |
  | 新增了子表与主表的级联逻辑 | 选择产品后，规格、单价自动带出来，不用查了再填 |

- 数字显性保留：素材里出现的数字（门店数、单量、金额、人数、频次）必须进报告并显性呈现，不许抽象成「多家」「大量」。数字是画面感和说服力的来源；素材没有的数字不编。
- 不用「您」「我们」「为您」等称谓，用「企业方」「双方」或直接以对象作主语。
- 名词只有两个来源：客户素材原话、平台官方名（版本与功能名以 references/platform-pricing.md 为准）。不生造行业黑话。
- 素材里没有的事实不编。缺价格、数量、日期等关键信息时写（待确认）并在交付时向用户列出清单。
- 人物称谓全篇统一（如素材里「股东」「老板」「领导」混用，先向用户确认统一叫法）。
- 涉密内容（内部系统地址、协议参数、未公开价格政策）不写入报告。

## 各章写法

**封面区**：kicker 是行业词、字间空格；主标题固定「{客户简称}数字化建议报告」，不加"服务包版"等后缀。核心目标一段四要素：以什么为切入点 → 用什么替代现状 → 达成什么可见效果 → 划出什么边界，**全段不超过 120 字**。

**一、企业与现状概览**：factlist 四条 dt 固定（行业与业务模式 / 组织规模与协作结构 / 数字化现状 / 项目目标），每条一段散文，不套卡片，**每条不超过 3 句、约 100 字**。只留支撑后文诊断的事实，经营细节与数字留给诊断卡用，不在概览里先讲一遍。数字化现状末句点出协作断点。项目目标只写一句（≤60 字）：是封面核心目标的一行浓缩，不复述边界与替代对象。

**二、核心痛点**：开场一句固定句式。诊断卡 **4 或 6 个（必须偶数）**，两列网格。卡名是名词短语（≤14 字），点出缺失或失控的对象；描述写成**真实业务场景**：谁、在哪个业务环节、具体发生了什么（用素材里的真实场景，不抽象概括），再接一句后果（能量化就量化），**合计 50 至 100 字**，念出来要有画面，让客户觉得「这说的就是我们」。

**三、建设目标**：开场一句话过渡。目标 **3 至 6 项**，每项 h3 一句动宾短语（≤16 字）＋展开**一句话**（做成什么样＋终结什么现状，≤60 字）。

**前三章总闸**：封面到第三章结束，诊断卡 4 个时合计不超过 1200 字，6 个时不超过 1500 字。同一事实全篇只出现一次：概览铺背景、诊断给后果、目标给动作，三章不互相复述。

**四、数字化解决方案**：note 说明文字模板里已固定。note 之后是**未来业务全景流程图**（模板 .flow 结构）：环节按客户业务主流程排 4-7 个，卡内只放环节名（≤6 字），不加承接模块等附注文字；流程图前一句短引入，**不罗列环节名**（环节让图自己说，文字重复念一遍等于把图讲两次）。每个模块：

- h3 亮点标题用「功能点，业务成果」两段式：前段说系统做什么，后段说业务得到什么，两段都是大白话短语，**合计 10-18 字，禁止压成四字对偶**
- fn 是模块业务名；要点 3-4 条，短句，不解释原理。**每条要点都要带成果**：前半句说系统把什么事接过去了，后半句说这件事从此变成什么样（少了哪道人工、省了多少时间、哪本账随时能看、哪个风险不再发生）。只写动作不写成果的要点（如「每日归集门店销量与库存」）不合格，要写成「门店销量库存每天自动归集，不用再逐店手工汇总」这样读完能感到降本提效控风险的句子
- 模块与诊断的对应关系必须全覆盖：每条诊断至少有一个模块回应，每个模块至少回应一条诊断，无一悬空
- 讲同一对象的多个小模块合并成一个主模块，用篇幅体现主干；边角能力不单列
- 图：成文阶段不放图也不留占位。用户确认配图后，在模块末尾追加 .fig.shot 的 img（alt 与 h3 完全一致），PNG 用 scripts/embed_figures.py 嵌入

**五、数字化实施路径**：阶段卡 2×2，通常四段：需求梳理与结构设计 → 最小闭环搭建 → 迭代扩展 → 培训与交付，按项目实际增删。每卡写清这个阶段做什么、交付什么。总周期区间写在开场句。

**六、投入与报价**：A 平台订阅的版本选择与价格查 references/platform-pricing.md；B 服务包的定价、包数建议与核销口径查 references/service-package.md。规格说明栏写该客户用得上的能力，不罗列参数。合计行只填总价。三条备注结构固定：版本选择说明 / 服务包起售与核销方式 / 后续迭代方式。

**七、预期核心业务价值**：两卡固定（对于决策层 / 对于一线团队），各 3-4 条，每条须能回扣到某条诊断或目标，不写空泛收益。

**八、下一步行动清单**：默认五条已在模板里，按项目微调。付款表述用「企业方完成付款」，不写「支付首款」。

**九、附件**：四条默认超链接已在模板里，一般不动；客户有专属附件时追加。

**尾注**：两段固定句式，只改沟通日期。

## 交付前自检

1. 全文搜 `{{`，不得残留占位符。
2. 诊断 ↔ 模块 ↔ 价值三层对应关系逐条核过，无悬空。
   2.5 用「不懂系统的业务经营者」视角通读一遍：出现表结构、字段、自动化规则等实现细节词的句子改写成业务语言；诊断卡逐张检查是否为真实场景而非抽象概括；方案模块逐条检查要点是否都带成果后半句，只有动作没有成果的补上。
3. 报价数字与 reference 一致，合计算对。
4. 附件链接可点；已配图的报告，逐一核对每个模块 img 已嵌入非空 data URI。
